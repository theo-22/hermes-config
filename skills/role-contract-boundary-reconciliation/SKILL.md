# Role Contract Boundary Reconciliation

Turn a verified role-runtime inconsistency into one current, testable contract
without absorbing neighboring roles, shrinking the role below its job, or
widening capability.

## Governing boundary

Reconcile **contract, state, ownership, and existing authority**. Do not treat
this skill as authorization for:

- new tools or Stage 2 capabilities;
- role merging or fleet rollout;
- concept-map mutation;
- protected-surface changes;
- destructive cleanup;
- implementation-session self-acceptance.

Use `role-workspace-sufficiency` alongside this skill when the role lacks enough
continuity, scratch, staged, receipt, or telemetry space. Use
`repair-capability-truth` when the primary problem is live tool/schema/query
divergence rather than the whole role contract.

## Required authority and sources

Start from the routed work order, orchestration record, Project Room, or named
authority file. Before implementing a proposal, apply
`/Volumes/Extra/Substrate/_shared/Proposal_Provenance_Policy.md`.

Read only the directly relevant sources:

- completed review and independent verification;
- current role Home and runtime workspace;
- role launch registry and behavior floor;
- static role scope, write roots, and path resolvers;
- current MCP/server mechanics and focused tests;
- helper-profile continuity and recurring outputs;
- relevant shared doctrine:
  - `/Volumes/Extra/Substrate/_shared/Role_Runtime_Workspace_Sufficiency.md`
  - `/Volumes/Extra/Substrate/_shared/Role_Runtime_Workspace_Template.md`
  - `/Volumes/Extra/Substrate/_shared/Scope_Comparison_Protocol.md`

Treat memory, Pieces, tool descriptions, and old migration labels as leads only.

## Workflow

### 1. Enter lifecycle and claim

1. Confirm authority is current and the packet's stop condition is explicit.
2. Acknowledge the orchestration ID before mutation.
3. Claim the role Home, exact configuration files, exact tests, return receipt,
   and any shared closeout surfaces before writing.
4. Move lifecycle to active only after acknowledgement and claims.

If no lifecycle record exists, preserve the same ordering in a durable receipt:
authority → acknowledgement → claims → active work.

### 2. Snapshot live truth

Record:

- relevant paths and current file inventory;
- repository roots, branches, dirty state, and exact overlapping changes;
- current static tool set and count;
- current read/write roots and path fences;
- current root state, continuity surfaces, helper-profile state, and external
  dependencies;
- server process/health where access changes may require refresh.

Compare against the completed review. Report material drift before implementing
around it. Do not repeat a finished inventory as substitute for Stage 1.

### 3. Write the contract before changing access

Create or establish one canonical current contract covering:

- complete job and intended outcome;
- unique judgment or action owned by the role;
- explicit non-job and neighboring-role boundaries;
- normal inputs and evidence precedence;
- ordinary direct actions;
- criteria for entering Orchestrator-controlled lifecycle;
- outputs, return path, and stop condition;
- hazards, protected boundaries, and degraded mode.

Preserve strong role-specific behavior that still applies. Replace retired
mechanics in live instructions; retain useful rationale in clearly labeled
Reference or archive material.

### 4. Settle Home and continuity ownership

Create an ownership matrix for:

- root orientation and state;
- runtime continuity, scratch, staged work, receipts, and telemetry;
- helper-profile memory, reports, crons, and operational artifacts;
- inbound/outbound handoffs;
- external dependencies;
- verification evidence and archives.

Name exactly one canonical cross-session live edge. Classify every other state
surface as pointer, checkpoint, operational evidence, generated view, or
history. A Home is the role interface plus a record of external dependencies;
distributed footprint is not itself a defect.

### 5. Reconcile access from the job

Keep these evidence layers separate:

1. static configured scope;
2. server-advertised schema;
3. fresh-client exposure;
4. successful calls.

For each write root:

- name the concrete ordinary role job it enables;
- retain role-owned reversible authority needed for that job;
- narrow or remove unsupported generic external roots;
- prefer staged/routed outward work over ambient external mutation;
- do not add tools or widen roots during this stage.

Make consequential access changes exact-slice, reversible, and tested with both
allowed and denied paths. Preserve existing staged use cases when narrowing a
generic live root.

### 6. Repair the current orientation set

Reconcile the functional equivalents of:

- `README.md`
- canonical role contract or behavior overlay
- `CURRENT_STATE.md`
- `NEXT_ACTION.md`
- `AGENDA.md`
- `OPEN_GAPS.md`
- `TREE.md`
- continuity pointer
- capability truth and acceptance references

Do not make historical helper/profile state the role's root live edge.

### 7. Define lifecycle identity

State:

- what the role may deliver directly;
- what requires one Orchestrator orchestration ID;
- how acknowledgement, progress, return, verification, and acceptance travel;
- when the role resumes judgment after a return;
- which surface governs content and which governs lifecycle.

When inbox, work-item, and orchestration records refer to one lifecycle-bearing
job, keep one primary orchestration identity.

### 8. Return candidates without promoting them

Produce:

- actor definition candidate:
  `Job / Inputs / Actions / Boundary / Escalation / Record`;
- provisional relationships to neighboring roles/helpers;
- a short delta against the role-runtime enough-review template, separating
  reusable fleet pattern from role-specific choices.

Do not mutate the concept map or apply the pattern to another role.

### 9. Verify independently

Run deterministic implementation checks:

- exact static tool set/count;
- allowed role-Home path;
- denied unsupported external path;
- preserved staged path, if applicable;
- access-audit output;
- compilation, lint, and diff checks;
- service health after a controlled refresh, when required.

Use an independent read-only verifier that did not implement the change. If a
broad verifier times out, retain the timeout as non-evidence and split the proof
into focused contract/ownership and access/scope passes.

Do not claim fresh-client acceptance from the implementation session.

### 10. Return, record verification, and stop

Write one normalized receipt with:

- verdict;
- files/config changed;
- authority and claims;
- contract/ownership decisions;
- access before/after;
- tests and direct evidence;
- verifier identity, receipt, and verdict;
- unchanged surfaces and non-scope;
- deviations, unresolved contradictions, and exact rollback;
- actor candidate and fleet delta paths;
- separately authorized next-stage recommendation.

Respect lifecycle ordering. A common control-plane sequence is:

`active → returned → verification_pending → verified`

Do not call `accept_work` unless the packet grants acceptance authority and the
required fresh-session proof exists. Release every claim and stop at the packet
boundary.
